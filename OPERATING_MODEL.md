# ARC White-Box — operating model (2026-09-28)

One page. It maps the standing directive (simple compound graph + V-model rigor + recursive learning + SME-owned agents)
onto what already exists in this folder. No new tooling: the files below ARE the system.

## 1. V-model: every claim climbs these rungs, and each rung has ONE instrument
| rung | question | instrument (exists) | noise floor |
|---|---|---|---|
| Unit | Is one ReLU step right, given exact inputs? | one-step oracle from MC caches (`mc_cache_alllayers_*`) | MC 2e5 |
| Integration | Does the 16-layer chain compound correctly? | oracle injection into the chain (`proto_d21.py` pattern), MLPs 1000/1001 | 7e-8 (1e6 refs) |
| System | Is it better across the distribution, not on 2 nets? | `whest run --split mini --n-mlps 100 --runner subprocess` (official 1e9 refs) | ~1e-10 |
| Acceptance | Does the grader agree? | graded submission (≤ 3/day, self-imposed) → Private Re-evaluation | — |
Rules: pre-register the gate AND check its threshold is attainable by its own oracle (the D21 lesson). Nothing claimed
below a rung's noise floor. Submit only after the System rung (bar: predicted ≤ 0.8 × the current best graded).

## 4. Recursive learning loop (every gate, ~5 min)
After each verdict: (1) append the verdict to R2_GO_NOGO.md; (2) add a one-line lesson to §5 below if it would change
how the NEXT gate is designed; (3) promote lessons that generalise beyond ARC to Claude memory / the vault.

**Agent brief contract (the recursion; every delegated gate carries it):**
1. BEFORE: read §5 and name, in the R2_GO_NOGO entry, which lessons shaped the gate design.
   Every background job goes through `research/rebuild/bg.sh`; `bg_audit.py` must be clean of your own jobs before you report (rule 14).
2. AFTER: append ≤ 2 new lessons to §5, and only ones that would change how the NEXT gate is designed.
3. The orchestrator's verifier checks both steps. A lesson that changes nothing is dropped; a lesson that recurs is
   promoted to Claude memory / the vault so it survives the competition.

## 4b. Learning from entries (three loops)
1. **Our entries = instrument calibration.** Every graded submission adds a row: predicted (Mini-100) vs graded → offset.
   v1 +2 %, v3 +4 %, v5b +2.8 % (Mini 6.88e-8 vs graded 6.69e-8): stable, Mini-100 reads ~3 % pessimistic. A drifting offset means the System rung has decoupled from the grader: recalibrate.
2. **Entries as controlled experiments.** Each submission changes ONE thing vs its predecessor and carries a written
   prediction (in PROGRESS.md before submitting). The grader (1e9 truth) is the independent verdict on that change.
3. **Others' entries (public only):** `research/leaderboard_snapshot.py` daily (cron 06:13) → `research/leaderboard/<date>.csv`
   + SurrealDB `leaderboard_snapshot`. It captures exact utilization (J2W 0.108, Luna 0.134…). Watch for: method jumps (raw
   MSE steps), anyone under the 1.33e-8 wall, the utilization spread. No code, no error-message mining.
4. **Forum (read-only; user decision: we never post):** `research/forum_watch.py` daily (cron 06:41) lists new/updated
   threads → read prose only → FORUM_DIGEST.md "Updates". Assume others found what we found: credit them in the
   write-up, and look for what they found that we haven't (cost ideas especially).

## 5. Lessons (each changed a later gate)

> **Standing rules (read these first; distilled 2026-10-12 from the ~45 lessons below — the full list stays as evidence):**
> 1. Judge every change WITH the shipped learned head in the loop; an uncorrected pass is a hypothesis (7/7 failed net of head: G-RB13/33/54b/59/61/73/76; mechanism G-RB73: the head already owns the state-predictable part).
> 2. Phase-2 policy (2026-10-12): no more upstream-accuracy levers; fund only output-identical cost ratchets, residual engineering and designation safety.
> 3. Pre-register the bar, the kill rule and the prediction with an ISO stamp BEFORE the run; self-label the verdict; the output file must post-date the registration.
> 4. Timing is judged against a same-session control, never an absolute or an old baseline; the worker's own VmPeak and residual are the instrument (in-process numbers understate both). When only the timing rung is open on an OUTPUT-IDENTICAL candidate and slots are spare, a grader run is a valid instrument (v77_fsc, 2026-10-12).
> 5. Recompute every cited cost/util number in budget units yourself (K=2 "0.11" was 0.055; sampled-κ4 "+1.5 pt" was 15 util; prune "0.941" was 0.957 metered).
> 6. Decompose before you build: cross term with the inherited error (oracle → predictor), sector cross-correlation (carrier), rank profile (compression), cost ledger in n³ units (re-association) — each is a minutes-long read that has killed hour-long prototypes. Count the terms of a pulled-back object before costing an adjoint: a single-read-layer pullback is O(L n³), every-layer reads are Θ(L²n³) (G-RB81).
> 7. Verify an agreeing result harder than a disagreeing one; a check that cannot fail proves nothing — every PROVED claim carries a perturbed run that must fail.
> 8. A few-% lever needs VALID-20; a <1 % lever is below what the grader resolves — do not spend a slot on it.
> 9. Query the ledger (`gate_ledger.py query`) and run every candidate through `ladder.py`; consolidate new lessons into this header the same day they land.
> 10. **Tier every agent by its job (2026-10-13; per published model positioning, platform.claude.com):** Haiku 5.5 (`model: 'haiku'`, effort low/medium) for extraction, classification, routing and claim-to-source lookups; Sonnet 5.5 (`'sonnet'`) for write-up drafting, revisions, summaries and second-pass verification; Opus 5.5 only where a confident mistake is expensive (gate design, ship decisions, adversarial review of a submission); Fable only for genuinely novel derivation. Default-inheriting the session model is a usage leak.
> 12. **Workflow cost (measured 2026-10-13):** the untiered V13 claim audit (57 agents, all on the session's Opus) used ~19M subagent tokens, a third of a 5-hour window. Tier the stages before launching (rule 10), and never tell a refuter to 'default to upheld': it refuted 0/32, so the applying agent had to re-verify every item anyway.
> 13. **Unattended jobs (2026-10-13 post-mortem):** anything that must run while the user is away goes in a persistent scheduled task, never a session-only cron (one never fired overnight); every network call in an unattended prompt carries a hard timeout and a 'log FAILED + notify' exit (a hung fetch blocked the daily watch for two days, and the scheduler then refused every later run as 'already running'); check a scheduled task's run history before relying on it.
> 14. **No immortal background work (2026-10-13):** start every long-running or waiting job with `research/rebuild/bg.sh <max-hours> <label> -- <cmd>` (enforced deadline + registry; never bare `&`, `nohup` or `until`). Before reporting, an agent runs `python3 research/rebuild/bg_audit.py` and stops or hands off anything of its own still running. The orchestrator treats a harness note 'stopped with background work still running' as an action item: stop the agent unless that work is needed. (One agent kept children alive 115 h; ~20 such tasks piled up unseen because agent shells cannot list host processes.)
> 11. **Tools that replace hand steps:** `research/rebuild/submit.py <build> --predicted X --basis "..."` (refuses without a prediction; logs PROGRESS + `calibration.jsonl`; `--report` prints graded/predicted, median 1.000 over 4 as of 2026-10-13); `research/rebuild/workflows/claim_audit.js` (tiered claim-to-source audit of any document: Workflow scriptPath + args {doc, out}); ladder.py now defaults to PSI log-only and a 7900 MiB worker bar.
- A threshold must sit above its own oracle's attainable value (D21: 1.5e-7 vs an oracle at 1.6e-7).
- Read the author's diagnostic rows yourself: the D21 agent's "not κ4" was inverted by its own numbers (82 % / 71 %).
- A verification that never ran is not a verification (the indep_v3 script didn't exist the first time).
- 2 local nets can't resolve ±10 %; the System rung (100 official nets) is required before claims or submissions. Calibrated: Mini-100 = grader within 2–4 % (v1, v3); 5 nets can read 2x off.
- The top of the leaderboard is decided by budget share (10–18 %) as much as accuracy: port cost matters.
- A one-step PASS doesn't imply an end-to-end gain: errors can cancel (v3's low Σ offset its high κ3). Always run the e2e rung.
- Accumulation is mostly incoherent (depth exponent 1.35): per-step accuracy gains square in final MSE (Lemma 4).
- A check that has never failed proves nothing: every PROVED result carries a perturbed run that must FAIL (PROOFS.md).
- Re-read the "why" of an old NO-GO before re-attempting its family (the forum's dead end = our R2 at 9.1e-7).
- A timeout is an instrument failure, not a verdict: 5/5 NPU "wrong" labels were router-queue timeouts.
- A single same-order term added without its formal partners (κ3²/72 without κ5/κ3κ4) is not guaranteed to move the truncation error in the "helpful" direction — it moved it the wrong way on G-V4, consistently, in isolation and combined.
- A mean-only ("readout-only") correction that skips the matching covariance-series row breaks the k=0 cancellation identity one layer downstream; a term that looks like it "hurt" may really be an incomplete patch, not a wrong derivation — disentangle before concluding the theorem is wrong (G-V4, unresolved).
- Energy share does not price a coherent term: the E-leg exclusions were 0.3–4 % of the energy and cost +9 % e2e (a bias, not scatter). Price a dropped term by its e2e run, never by its norm.
- Read the adjusted score along the whole budget axis before gating on raw MSE: lever A's frontier is MSE ∝ budget^−0.35, so every point above the 10 % floor scores worse than the floor — a "≤ 10 %" gate was the right question but "≤ 2.5e-7" was the ceiling, not a target.
- A plain-English task description ("port A + B") can silently name the wrong base if A and B were designed against different oracles: `proto_leverA` fed both D22 and D31 into its base, but v4_zc (the literal "A") is D22-only. Re-derive the port target from the code the numeric gate thresholds actually came from, not from the description, before writing anything (G-V5-PORT).
- **The BudgetContext in-process residual measurement and the official `--runner subprocess` residual measurement are NOT interchangeable — only the second is the grader's actual cap.** v5's direct `residual_wall_time_s` was 239–275ms (PASS vs 400ms), but the real `whest run --runner subprocess` check the gate also pre-registered showed the SAME MLP "exhausted residual" at 552ms and got zeroed (garbage MSE 1.51). The subprocess runner's IPC/serialization overhead is real grader-representative cost the in-process check cannot see. Never report a residual-time gate as PASS from BudgetContext alone when the subprocess check was pre-registered too — run both, and if they disagree, the subprocess number is the one that matters.
- `ulimit -v` breaks `whest run --dataset` (the 6.3 GB mmap counts as virtual memory → MemoryError): the cap is for numpy jobs, not the official runner.
- One failed MLP in 100 (zero-fallback 0.98) swamps any accuracy gain by ~10^5x: gate on 0 failures on the full Mini-100 and on residual MARGIN (max, p99), not the mean.
- A mechanical audit beats a grep: `warnings.filterwarnings("error", message=".*auto-routed.*")` around a `setup()`-driven `predict()` call caught an unbilled-scalar-arithmetic bug (integer-indexing a FlopscopeArray unwraps to a host `numpy.float32`) that a `grep '\.item(\|float(fnp\|bool(fnp'` audit cannot see — and a refactor FIXING one instance of this bug (v5_leverA's `w.g[i]`) introduced a fresh, self-inflicted instance of the exact same class (`inv_fact_d22[k]` indexed inside a new Horner loop). Re-run the mechanical check on the new code, not just the code it was copied from.
- A verifier that bypasses a production entry point (here, `Estimator.setup()`, in favor of directly setting `e._g = [...]`) inherits none of that entry point's failure modes — it built 0-d FlopscopeArrays via `fnp.array()` while the real `setup()` built host scalars via integer indexing, so the bug was invisible to the verifier from day one. Always add at least one check that drives the real API.
- Heavy machine load can manufacture failures: v4 failed 1/100 at load 54–100 and 0/100 at load ~12. Run the System rung ALONE, and record uptime with it.
- A per-layer residual profile must carry its per-layer noise floor: the MC noise of the two-index sector scales as 3σ_z⁶/N, so the same 2e5 cache is 0.43 of T's m.s. at layer 2 and 0.005 at layer 16 — the chain's "0.365 at layer 2" that anchored the G-D21-2 pre-registration was the reference's noise, and a rung was designed around it (proto_gaphunt, 2026-09-28).
- A one-step oracle test of a CHANNEL (birth exact to the floor) does not test the channel's STATE (the aged stack was 30 % wrong while every birth was exact): when injecting the exact value of quantity X at every layer leaves the next layer's residual unchanged, X is not where the error is made — instrument the channel that X never feeds (per-step injection + aged-stack-vs-oracle, `proto_gaphunt_e2e.py --stepwise`, `proto_gaphunt_aged.py`).
- Fewer flopscope-dispatched calls does not imply less residual time: fusing two independent per-layer Horner recursions into one over a concatenated (K,11,n,n) tensor cut the dispatch count ~12% but made residual time ~30% WORSE (v5c bisection). Residual is wall minus flopscope's own backend+overhead timers (`_budget.py`), so the concatenate's 928ms and the higher multiply/add times it also measured are BACKEND, not residual, by definition — they cannot be the direct cause. The evidence instead points at cProfile's own `predict()`-frame tottime, which rose ~3x (0.044-0.057s in v5b to 0.164s in the fused variant) alongside the residual increase: the likely mechanism is CPython-level cost (allocation/refcount/GC) of rebinding a ~400MB combined array on every layer, which happens OUTSIDE any flopscope-timed span and so is invisible to flopscope's own accounting — a HYPOTHESIS, not confirmed by a dedicated instrument. Bisect and measure each residual-reduction candidate in isolation (interleaved trials against the same baseline) before combining them; never trust "fewer calls → less residual" by assumption, and never attribute a residual change to a mechanism (like a slower backend op) that the accounting identity rules out.
- Record the grader's submission ID in the PROGRESS.md table at submission time: the write-up must cite exactly one graded ID (rules §6), and the v3/v5b rows carry only "(v3)"/"(v5b)" — the ID had to be flagged as a human TODO in `writeup/PHASE2_WRITEUP_V2.md` because it exists nowhere in the workspace (surfaced 2026-09-28 while writing).
- Run every System-rung (Mini-100) instrument with `--format json`, never text only: the v1/v3 runs kept only the aggregate table, so their per-layer and per-MLP residual data cannot be plotted (write-up figures F1/F6 have v4_zc and v5b only) and the v3 "0 failures" cannot be re-read per MLP.
- Consistency is not accuracy: the formally complete same-order Edgeworth set (κ3²/72 WITH its k=0-consistent covariance rows) still cost +0.16 % e2e in every consistent form; the mean-only patch's +0.74 % was ~80 % identity break, ~20 % the term. Before gating any readout-series term, price it against GAP §2's last-layer oracle floor (3.1e-10 ≈ 0.5 % e2e) — a 3 % bar on a 0.5 % ceiling is a pre-registered FAIL, and the informative sub-gate ("does the consistent form stop hurting?") is the one to design (G-E6).
- A derived coefficient can be robustly the right SIGN and the wrong SIZE: the κ4 mean coupling μκ3 exists on 8 nets × 14 layers (slope 0.15–0.3 g, sd 0.03–0.06) yet the zero-constant g is 4–7× too large and worsens the estimate. When a model has two observable predictions (here the κ3 and κ4 mean terms) check BOTH at the unit rung before building the estimator — disagreement on the shared factor falsifies the model, and fitting the factor would be a new constant that here captures ≤ 1 % anyway (G-K4I).
- A "compression" billed per retained direction must be compared with the EXACT cost under the SAME algebra before any rank is chosen: under S-0 an exact cohort costs 12 units and a rank-r one 20·r/n, so the break-even is r ≈ 0.6n and the whole age-2 tier (r_99 ≈ 0.5n) was a wash — the design moved from "compress everything" to "compress from age 4" on that one number (SECT_COST, 2026-09-28). Derive the break-even first; it decides WHERE a lever applies, which the oracle's fidelity table alone cannot.
- A truncation is a committed, persistent error, not a per-layer one: the propagator after the cut is independent of the dropped directions, so the relative error stays at its age-of-commitment level while the oracle (re-truncating at every layer) keeps improving. Consequence: few large rank steps beat many small ones at equal cost (4 steps 1.243e-7 vs 9 steps 1.376e-7), and an oracle that re-optimises at every layer is a LOWER bound on a design that commits — write the bias down before predicting from it (SECT_COST, 2026-09-28).
- Our own concurrent agents are the main source of load: schedule Mini-100 runs in a window with no heavy agents running, not just a moment when load happens to be low.
- A same-oracle-pair A/B ratio is immune to a shared calibration constant that neither arm's absolute value is: `g_table` was fit only on the in-house generator's train MLPs and never checked against official weights, yet base/sect/sect+excl all use it identically, so G-SECT-VERIFY's 7.7-9.2x replication on the official Mini split is trustworthy evidence for the derivation even though the absolute g_table calibration on official weights remains unverified — when re-scoring on a new oracle, check whether the candidate's unverified inputs cancel in the comparison you're actually gating on, not just whether they're calibrated.
- A sign-flip mutant on a correction term that feeds back into an AGED, iterated stack (not a single readout) can fail by 4+ orders of magnitude rather than by a modest degradation, because the wrong sign turns a negative-feedback stabilizer into positive feedback across 16 ReLU layers — a mutant result "too extreme to be informative" is itself informative about the term's dynamical role, and a milder degradation should not be assumed to be the only valid discriminating outcome.
- A checker's own truncations are part of the instrument: check9's first normal run FAILED at J = 5,6 because the expansion side kept 12 covariance-series terms while f̂_k grows like √k! — a ~1e-8 tail whose ε-dependence looked exactly like a missing ε³ term in the theorem. The univariate control (k = 0 term alone) and a per-k test (each F̂_k separately) passed, which localized the fault to the checker; the theorem never changed. Before reading a normal-mode FAIL as a wrong theorem, decompose the check into pieces that a known-good check already covers and find the piece that disagrees (PROOFS Prop 9, 2026-09-28).
- The same exponent-style number can be honestly measured several ways and they need not agree: Lemma 4's depth exponent (1.35: K2 chain, μ_z, 6 local nets, noise-corrected) and F1's (1.55/1.58: v4_zc/v5b, h_l per-layer MSE, 100 official nets; 1.19/1.28 over layers 8–16) are different chains, quantities, net sets and fit windows on a concave log–log curve. When two documents quote one "p", write down all four attributes next to each number rather than declaring one of them wrong (PROOFS §4 reconciliation note, 2026-09-28).
- Before claiming a derivation as ours, search the organizers' paper INCLUDING its appendices and public code: G-SECT turned out to be ARC's own "diagonal adjustment" (arXiv 2605.05179 §S.4.3 (d)ii, eq. 17). The appendix, not the main text, held it.
- Batching per-cohort operations into `fnp.einsum` calls over a stacked tensor cuts flopscope OP COUNT
  (dispatch overhead, the G-V5-RES/v5c residual-time lever) but is NOT a FLOP reduction: the billed FLOPs
  of one batched contraction over c cohorts are the same order as c separate per-cohort matmuls. G-V6-PORT's
  batched sect-chain port billed 157.91% of budget (f32) -- MORE than SECT_COST.md's own unbatched
  per-cohort hand ledger (144.6%) for the identical algorithm. Fixing residual time (op count) and fixing
  FLOP budget (gate c) are two separate gates; passing one says nothing about the other, and a design
  motivated by the first can still fail the second on the very config it was built to make submittable.
- When a hand-maintained FLOP ledger and flopscope's own live `BudgetContext` metering disagree by double
  digits of percentage points on the IDENTICAL algorithm, trust flopscope's number for any gate decision --
  a hand ledger is a planning estimate, not the grader's instrument (generalizes the G-V5-RES "in-process
  vs subprocess residual, only one is the grader's cap" lesson to hand-ledger vs live-metered FLOPs).
- A hand ledger built from an algorithm's exact per-item call sites can still mispredict a BATCHED port's
  cost even when its formulas are individually correct, because uniform tensor-stacking removes item-level
  special-case discounts (a None-valued leg, an implicit-identity shortcut) the original per-item loop got
  for free -- diagnose by dividing flopscope's own per-(op_name,subscripts) `op_log` totals by the summed
  leading batch dimension to get a measured per-item rate, broken out by item age/type, not as one
  aggregate number (G-V6B: 157.91% vs 144.6%, ~fully explained by this + a 15-cohort-layer count mismatch).
- Near a gate margin, an extrapolated correction factor measured on a DIFFERENT config is not decision-grade
  when the multiplicative-vs-additive reading of that correction alone spans the distance to the threshold
  (G-V6B: P4-192-K8 reads 82.0% / 89.5% / ~94.9% depending on correction model, straddling the 90% gate) --
  direct metering of the actual candidate is required whenever the estimate's own uncertainty band straddles
  the threshold being gated on.
- A cost floor is a property of the ALGEBRA it was billed in, not of the representation: SECT_COST's "42 % floor" (12 units per cohort-layer) fell to 58 % for the whole untruncated chain once the stack's coincident objects were read from its own previous-layer readout (S-1: N/M′ were recomputations) and the correction's k = 1 part was born into the legs. Before declaring a floor, list which billed products recompute something the chain already holds (SELF_BIRTH, 2026-09-28).
- An impossibility proof for the EXACT identity does not settle the cost question: the per-layer coincident correction provably cannot be folded into the birth, yet its irreducible remainder after the k1 leg was 1 % of T and dropping it cost 6 % e2e. Prove the exact claim, then MEASURE the order of what remains and let the e2e run — not the proof — decide whether to carry it (SELF_BIRTH, 2026-09-28).
- A hand-ledger op-count estimate for one algorithm does not transfer across porting STRATEGIES of that same algorithm: SBk1's "1,773 ops, fewer than v5b's ~3,769" (per-cohort-loop hand ledger) predicted a fast port, but a literal per-cohort Python-loop port measured 6,123 flopscope ops and 342.5 ms residual — over the 250 ms cap — because flopscope counts every primitive numpy call, finer-grained than the hand ledger's per-formula tally, and per-call dispatch overhead dominates a growing per-layer loop. Batching the identical algorithm into a stacked-tensor einsum cut it to 4,606 ops / 212.8 ms.
